## 0. 원칙 — "3영역은 교육적 정보 계층의 세 축"

교사 팀이 T-CID 모형을 수행할 때, UI는 단순 탐색 위젯이 아니라 **교수학적 사고를 지지하는 구조**여야 한다.

| 영역 | 교수학적 역할 | 교사가 이 영역에서 얻어야 할 "1번 정보" |
|------|---------------|----------------------------------------|
| 상단 StageBar | **전체 궤적 인식** (모형 차원) | "나는 지금 T-CID 주기 중 어디에 있는가, 이 단계가 전체 설계에서 왜 필요한가" |
| 좌측 ActivitySidebar | **단계 내 순서·연결 인식** (단계 차원) | "이 단계의 활동들이 어떤 논리로 이어지며, 지금 활동이 왜 이 시점에 오는가" |
| 우측 ArtifactPanel | **산출물 간 누적·제약 인식** (활동 차원) | "지금 작업이 이전 산출물을 어떻게 계승하고, 이후에 어떤 제약이 되는가" |

→ 셋 다 "진행률 바" 이상이어야 한다. **교사가 스스로 "왜"를 재구성할 수 있게** 해야 한다.

## 1. 상단 StageBar — 교육적 정보 계층 제안

### 1-1. 현재 상태 관찰 (`src/components/stage/StageBar.tsx`)

- 5단계 노드 + 단계별 아이콘·색상 + 진행률 chip + 가드레일 배지(Ds) + E→T 순환 화살표 — **시각적 뼈대는 우수**.
- 현재 노드는 `label`과 `완료/전체` 숫자만 보여줌 → 단계명은 보이지만 **"이 단계의 교육적 역할"은 호버·클릭 전에 보이지 않는다**.
- Backward Design 표식(Ds가 평가 먼저)이 Ds 노드 자체에는 없음 (사이드바 범례에만 존재).

### 1-2. 필수 정보 우선순위 (StageBar에서 드러나야 할 것)

| 우선순위 | 정보 | 현재 상태 | 제안 |
|----------|------|-----------|------|
| P0 | 현재 단계 식별 + 5단계 궤적 | 있음 (노드 애니메이션) | 유지 |
| P0 | 단계별 진행률 (완료/전체) | 있음 | 유지 — 단 "산출물 확정 기준"임을 툴팁으로 명시 (status ≠ 산출물) |
| P1 | **단계의 교육적 명제 1줄** ("T단계 = 팀 정렬", "A = 분석, Ds 가드레일 생성") | 없음 | 노드 호버/포커스 시 단계 카드 tooltip에 노출. 노드 아래 subtitle 한 줄도 후보. |
| P1 | **A→Ds 가드레일 관계** (현재는 Ds 배지만) | 부분적 | 가드레일 배지를 A-2-3 노드(A단계)에도 표시 + A→Ds connector에 점선 방패 흐름 |
| P2 | **Backward Design 표식** (Ds는 평가 먼저) | 사이드바 범례만 | Ds 노드에 별(★) 코너 배지 추가 |
| P2 | E→T 순환의 "차기 주기 T는 이번 E 성찰의 산물" 의미 | 라벨 "새로운 주기 시작"만 | 호버 시 "E-2-1 팀 성찰이 다음 T-1-1의 입력이 됩니다" 안내 |
| P3 | 단계 이동 가능/불가 (호스트/팀원) | 클릭 가능 여부만 | 툴팁에 "권한 근거" 분리 표시 |

### 1-3. v2 스펙 접점

- **§3 가이드 역할** — 가이드 카드(`📍 현재 / ✅ 완료 / 🔄 지금 / ⏭ 다음 / 💡 왜 중요`)는 채팅에서 노출되지만, **StageBar는 이 카드의 "📍 현재" 라인을 UI로 상시 시각화**해야 한다. 채팅을 놓친 교사(뒤늦게 합류)도 StageBar만 봐도 자신의 위치·다음을 알 수 있어야 한다.
- **§6 의미 부여 역할** — 단계 전환 시 에이전트가 연결 멘트를 주지만(T→A: "비전이 수업 주제로 연결됩니다"), 이 전환은 StageBar의 connector에서도 **한 번 더 visual로 확인 가능**해야 한다. 단계 이동(클릭) 확인 모달에 "이번 단계에서 쌓은 것이 다음에 어떻게 사용되는지" 한 줄 인용이 들어가면 좋다.

### 1-4. 구현 제안 (ui-designer용 인풋)

```
[StageBar 노드 호버 tooltip 내용]
  - 단계 한 줄 정의 (예: "A = 수업의 뼈대 — 이 단계 산출물이 Ds의 제약이 됩니다")
  - 대표 활동 2-3개 목록
  - 이 단계가 "가드레일을 생성"/"가드레일을 소비" 여부 표식
  - 호스트 한정 "이 단계로 이동" 버튼
```

→ 현재 sidebar에 중복되지 않도록: sidebar는 "진행 중 단계 깊이 보기", StageBar는 "전체 궤적 + 단계 간 관계".

## 2. 좌측 ActivitySidebar — 교육적 정보 계층 제안

### 2-1. 현재 상태 관찰 (`src/components/activity/ActivitySidebar.tsx`)

- 단계 아이덴티티 헤더 + 팀이 할 일(3항목) + 활동 리스트(상태/가드레일/백워드 표식) + ACTIVITY_INFO 카드 + 단계 분석 버튼 — **정보 밀도 높음**.
- `ACTIVITY_INFO`는 훌륭함 (각 활동의 "무엇 + 왜 + 예시"). 단, **현재 활동만 보여주며 "직전·직후 활동과의 관계"는 부재**.
- `completed/warning/active_return` 아이콘은 있지만 **교육적 해석**이 약함 — warning은 "건너뜀"만 표시, 왜 건너뛰어도 되는지/언제 돌아와야 하는지 안내 없음.

### 2-2. 필수 정보 우선순위

| 우선순위 | 정보 | 현재 상태 | 제안 |
|----------|------|-----------|------|
| P0 | 단계 내 활동 순서·현재 위치 | 있음 | 유지 |
| P0 | 활동 상태(완료·건너뜀·재검토·대기) | 있음 | 상태별 **교육적 설명 라벨** 추가 (아래 §4 참조) |
| P1 | **활동 간 전환 이유** (T-1-1 → T-1-2: "비전이 수업 방향의 기준") | 없음 | 활동 카드 사이 미니 connector에 한 줄 ("비전 → 방향") 삽입 |
| P1 | 단계 전환(T→A) 순간의 **연결 메시지** | 없음 | 마지막 활동 완료 시 sidebar 하단에 "다음 단계 A에서는 이 T의 비전을 기준으로 주제를 선정합니다" 카드 출현 |
| P1 | 가드레일 표식(A-2-3) + 백워드 첫(Ds-1-1) 의미 노출 | 아이콘만 | 아이콘 옆 1줄 ("이 산출물이 Ds 전체 설계의 제약") |
| P2 | **팀원 탐색 모드**일 때 현재 활동과의 관계 | "탐색 중" 배너 있음 | "호스트는 {활동}에서 진행 중 — 이 활동은 {관계: 전 단계/다음 활동/건너뜀}" 형태로 교육적 맥락 부가 |
| P2 | 건너뜀 활동이 다시 필요해지는 트리거 | 없음 | "지금 방향이 이 활동 없이는 불완전" 판단 시 warning 카드에 "되돌아가기 권장" 이유 문장 |

### 2-3. v2 스펙 접점

- **§3 가이드** — `STAGE_GUIDE`(팀이 할 일 3항목)는 좋은 출발점. 단 **현재 활동별로 동적 전환**이 약함(단계 단위 고정). 활동이 바뀌면 "이 활동에서 팀이 지금 할 일"도 바뀌어야 한다. ACTIVITY_INFO의 body를 그 슬롯에 편입 가능.
- **§6 의미 부여** — 활동 선택 시 ACTIVITY_INFO가 뜨는 것은 **절차적 의미**는 주지만 **교육철학적 의미**(이 활동이 교사에게 왜 중요한지)는 약함. 예를 들어 Ds-1-1은 "백워드 설계"라는 교수학 원리를 체화하는 지점인데, 카드의 설명은 기능적 정의에 머뭄.
  → 카드 하단에 **"왜 이 활동을 하는가 (교사 관점)"** 한 줄 (예: Ds-1-1 → "평가를 먼저 정함으로써 활동이 목표에서 이탈하지 않습니다").

### 2-4. 구현 제안 (ui-designer용 인풋)

```
[ActivitySidebar 개선]
1. STAGE_GUIDE.teamTasks를 현재 활동 기준으로 1-2개 동적 교체
   (예: viewingActivity=T-2-1일 때 "각자 강점을 확인하고 역할을 나눠요")
2. ACTIVITY_INFO 카드에 필드 추가:
   - whyNow: "왜 지금 이 활동인가" (직전 활동 산출물과의 연결)
   - warningRecoveryHint: 건너뜀 상태일 때 왜·언제 돌아와야 하는지
3. 활동 리스트 아이템 간격에 connector: 산출물 흐름 있음/없음 표시
4. 단계 마지막 활동 완료 시 sidebar 하단에 "단계 전환 카드"
   (v2 §3 단계 전환 연결 멘트 테이블을 이 카드로 렌더링)
```

## 3. 우측 ArtifactPanel — 교육적 정보 계층 제안

### 3-1. 현재 상태 관찰 (`src/components/artifacts/ArtifactPanel.tsx`)

- 현재 활동 산출물 헤더 + 상태 배지 + RequiredSectionsChecklist(E 단계) + 이전 산출물 참고 셀렉트 + 본문 렌더링 + 직접 입력 폼 + 버전 정보 — **기능은 충실**.
- **"이전 산출물 참고" 섹션**은 previousArtifacts를 모두 선택 가능하게 하지만 **"지금 활동에 왜 관련이 있는지"는 안내 없음**. 교사가 스스로 탐색해야 한다.
- A-2-3 가드레일이 Ds-X-X 산출물 작업에 **강제 참조되는 UI 장치 없음** (채팅 프롬프트에만 존재).
- 산출물 누적 관계(T-1-1 비전 → T-1-2 방향 → A-1-2 주제 → ...)가 **선형 리스트로만** 보이며 **"계승·제약" 관계**는 불명확.

### 3-2. 필수 정보 우선순위

| 우선순위 | 정보 | 현재 상태 | 제안 |
|----------|------|-----------|------|
| P0 | 현재 산출물 내용·상태·버전 | 있음 | 유지 |
| P0 | AI 초안 / 팀 확정 구분 | 있음 (StatusBadge) | 유지 |
| P1 | **이전 산출물의 "현재 활동과의 관계"** | 리스트만 | 각 이전 산출물 카드에 관계 라벨 (예: "기준", "제약", "직전 입력", "가드레일") |
| P1 | **가드레일 강조** (A-2-3을 Ds 작업 중에 상시 표시) | 부재 | Ds-X-X 활동 진입 시 A-2-3 요약 패널이 본문 상단에 상시 노출 (접기 가능하되 기본 펼침) |
| P1 | **RequiredSectionsChecklist**의 의미 | E만 있음 | T-1-1(비전), A-2-3(학습자 프로필), Ds-1-1(평가) 등 핵심 가드레일 산출물로 확장 |
| P2 | 산출물 확정의 **책임 소재** ("호스트가 확정함") | 자물쇠 있음 | 레이블 "팀 합의를 호스트가 대표 확정" 명시로 권한 근거 분리 |
| P2 | 산출물이 **어떤 후속 활동에 사용되는지** (forward link) | 없음 | 확정된 산출물 헤더 아래 "이 산출물은 {활동 목록}의 입력이 됩니다" |
| P3 | **빈 상태** 메시지의 교육적 성격 | "채팅 → 산출물" 도식 | "이 활동에서 무엇을 수집해야 하는지" 체크리스트형 안내 (가드레일 활동은 필수 섹션 목록) |

### 3-3. v2 스펙 접점

- **§3 가이드** — ArtifactPanel은 **"왜 중요한가"**의 시각화 채널. 가드레일 산출물(A-2-3)은 Ds 전 활동에서 **상시 참조 되는 "작업 환경 제약 조건"**으로 다뤄야 한다. 지금은 선택적 참조.
- **§6 의미 부여** — 팀이 확정한 산출물에는 **"이 내용이 의미하는 교육적 가치"**를 AI가 의미 부여한 한 줄이 함께 저장되면 좋다 (ARTIFACT_UPDATE 신호 확장 여지). 현재는 raw content만 저장.

### 3-4. 구현 제안 (ui-designer용 인풋)

```
[ArtifactPanel 개선]
1. "이전 산출물 참고" 리스트 → 관계 라벨 부여
   - 관계 타입: guardrail (A-2-3 → Ds*), 
              basis (T-1-1 비전 → 전 활동),
              prev_step (직전 활동),
              related (같은 단계 내 타 활동)
2. Ds 단계 활동 진입 시: A-2-3 가드레일 요약 카드 상단 고정 (접기 가능)
   - A-2-3 미완 시: "학습자·맥락 분석 없이 설계하면 가드레일이 없습니다" 경고
3. 확정 산출물 헤더 보조 텍스트:
   "이 산출물은 이후 [활동 코드 목록] 작업의 입력이 됩니다"
4. RequiredSectionsChecklist 확장 대상 결정은 별도 태스크
   (현재 E만 있음; 교육적 중요성에 따라 T-1-1/A-2-3/Ds-1-1 우선)
```

## 4. 상태 전환의 교육적 해석

> `completed`, `warning`(건너뜀), `active_return`(되돌아옴), `in_progress`, `not_started` — 단순 경고가 아닌 **교육적 의미**로 전달해야 함.

| 상태 | 현재 라벨 | 교육적 해석 | UI 제안 |
|------|-----------|-------------|---------|
| `completed` + 산출물 `confirmed` | 초록 체크 | "팀 합의로 입력을 확정했다" | 유지. "확정 시각 · 확정자" 툴팁 포함. |
| `completed` + 산출물 없음 | 체크이나 실제로 완료 X | **불일치 — 교사가 혼란** | 완료 기준을 **산출물 유무**로 단일화 (ActivitySidebar의 `effectiveStatus` 로직 이미 일부 반영). StageBar 진행률도 동일 기준. |
| `warning` (건너뜀) | 노란 경고 "건너뜀" | "이 시점의 논리적 순서를 생략하고 앞서 나갔다 — **나중에 반드시 돌아와 보완해야 할 부채**" | 경고 색 유지하되 문구를 **"미완성 — 다음 단계 진입 전 복귀"**로. 건너뛴 활동을 포함한 단계는 "부채 N개" 뱃지 노출. |
| `active_return` (되돌아옴) | 주황 "재검토 중" | "이미 확정했던 것을 재검토하고 있음 — 기존 합의가 흔들림" | 현재 아이콘(ArrowBendUpLeft) 유지. 본문에 **"이 활동을 재검토 중 — 기존 합의안을 확인하고 수정 근거를 기록하세요"** 배너 추가. |
| `in_progress` | 파란 시계 | "현재 팀이 작업 중" | 호스트 전용이면 Crown 아이콘과 함께. |
| `not_started` | 회색 | "아직 시작 전" | 단, "의존 활동이 완료되면 활성화"를 호버로 안내 (예: Ds-1-1은 A-2-3 없이 진입하면 경고). |

### 핵심 원칙

1. **"경고 = 실수"가 아닌 "경고 = 빚"** — warning은 교사 행동을 비난하는 것이 아니라, T-CID 모형의 논리에서 "아직 갚지 않은 설계 부채"를 알리는 것.
2. **active_return은 환영할 상태** — 팀이 스스로 설계 품질을 높이고 있다는 긍정 신호로 표현. 색은 경고색이되 문구는 "품질 개선 중".
3. **completed는 두 가지 층위** — 활동 status `completed` + 산출물 `confirmed`가 동시 성립해야 "교육적 의미의 완료". UI 전 영역에서 이 단일 기준을 공유.
